# 用户提议与确认：消息人工修订

> 本任务用户原意的归纳，不是逐字引文。确认口径见 [DECISIONS.md](./DECISIONS.md) §H；步骤、代码草案及验收见 [专项计划](./PLAN-message-reprocess-2026-10-15.md)。已允许开始分批实现，尚未整体完成，未部署。

| 编号 | 用户提议/确认 | 实现约束 |
| --- | --- | --- |
| P-01 | 纠正当时意思，不另造“后来改主意”分支；公平性由管理解释 | 原位置/时间不变，管理解释独立留档 |
| P-02 | 修订前条不能丢掉之后撤排等操作 | 重放当前完整流，不覆盖旧排位快照 |
| P-03 | 连续或不连续的补充性解释可手工合并 | 第一条完整替换、补充条拒绝，一笔事务，原行仍保留 |
| P-04 | 直接编辑动作 override，保留原自动处理结果 | 原文/自动结果/人工结果三层；空覆盖也有效 |
| P-05 | 修改优先名单不重跑 LLM | 动作已理解，只更新资格、排序与重算 |
| P-06 | 自动理解先于人工可观测动作 | 不设计“人工先忽略再首次自动理解”的倒序流程 |
| P-07 | 不需要二次确认；希望单步撤回 | 一次保存；完整逻辑检查点加逆事务，不丢新消息 |
| P-08 | 填 JSON 不现实，完整表单过于复杂 | 当前动作句点改；可选一句解释让 LLM 代填同一草稿，再手改保存 |
| P-09 | 排、撤不同语义；没再加排同商品则撤此前原位认购 | 不以邻接/间隔判断取消目标；测试紧跟及非紧跟 |
| P-10 | 先更新含代码片段的计划、决策与用户提议；冲突旧想法放原文档末尾 | 文档先行，逐批登记实测结果，不以计划冒充完成 |
| P-11 | 甲代乙排，乙在群内按乙权限、表里只写乙；匿名/群外/数字代号按甲权限，写甲(代标签) | 2026-10-22确认；唯一群成员匹配与真实发言人独立记录，同名/来源不明不猜，冻结旧归属；见DECISIONS §L |

仅隔离测试与占位数据；电脑端 1920×1080、100%；不碰真实群/配置、不部署、不重启常驻实例。此授权不等于整个 IA 重构、历史数据迁移或 Git 历史重写授权。

## 已舍弃的功能或思路

以下是讨论中助手提出、后被用户纠正或新口径替代的想法，不是用户仍在要求的功能：强制 LLM 重新裁定人工修订、预览后再次确认、独立订单联合解析、日常纠错改原文、填动作 JSON、覆盖旧完整状态来撤回、将排撤间隔误当合并问题。替代关系见 DECISIONS 文末及专项计划文末。
