## A. 业务口径

### A-1 减均 / 搜索 / 调价公式 `已决策`（2026-09-17，减均修订）
- **结论**：
  - **折扣最大化**、**调价**两条：按原建议口径通过（见 REQUIREMENTS §4.2/§4.3）。
  - **减均改为**：`B` = Σ各包**实付价**（优惠后）；`C` = **无折扣商品总价**；`G` = 已认购特典价合计；**总优惠额 `D = C − B + G`**；按**各商品自身标价**加权分摊 `D`；**只允许 2 位小数、四舍五入 + 残差校正**；**校验 `Σ商品减均后价 + G = B`**。
- 🟡**待确认**：`C` 是否**不含**特典价（我的理解：不含，`C` = 实购商品标价合计）；加权权重基数用 `C`。
- **影响**：`src/settlement/engine.rs`、`src/planner/**` + 全部单测。

### A-2 特典「实际认购」判定 `已决策`（2026-09-17）
- **结论**：认购在**排谷阶段**按「**成几开几**」——`granted_X = min(认购数_X, 实际成包数 P)`；超出部分**排失败/掉落**（不付款、不参与减均、不归属任何人）。
  - 3A+2B 认购、成 2 包 → `G=2A+2B`；成 3 包 → `G=3A+2B`。
- 🟡**待确认**：`P`（实际成包数）取自 ordering 引擎的排谷结果（唯一来源）。
- **影响**：`G` 与减均、应付金额。

### A-3 下单包模型 `已决策`（2026-09-17）
- **结论**：**一包 = 一份订单**；**不限制包数上限**；**包与商品认购之间不设任何校验联系**（两者解耦）；**特典不花钱**，下单时包总价**不计特典价格**。
- 🟡**待确认**：同一人可出现在多个包（因「无校验联系」，默认允许）。

### A-4 商品基础单价表 `已决策`（2026-09-17）
- **结论**：**无固定价目表，价格一律由管理员填写**（可编辑价格表）。通行证辅助规则：单价 **25/个**；**整盒 = 25 × 盒内个数**（非固定 175）；多数角色含精一/精二，未注明默认两件同购 = **50**，仅精一 = **25**；人事部简历总价视内含角色；风尚速递每角色 1 份；贴纸包内容不定 —— 均管理员填写。
- **影响**：需新增**管理员可编辑价格表**并接入结算 UI（原 T-01）。
- ⚠️ **部分已被取代（2026-09-24，见 G-6/G-7）**：`box_size`/`subitems[].pieces` 建模与「整盒 = 25 × 盒内个数」的目录表达**已废弃**；改为商品级仅原价、子项 A/B、整盒为独立种类。**「无固定价目表、管理员填写」结论继续有效**。

### B-5 临近同发送者消息合并理解 + 匿名代排 `已决策`（2026-10-13）
- **结论**：
  - **合并**：同发送者、消息流**相邻**（无他人插话）、**同意图**（Claim/Cancel/Modify 各自成组）的多条消息视为一个理解单元；**无时间窗口**；**普通闲聊/模糊表述（如"想要"）不算 claim、保持 `Ignored`、单例且断开**；`代排` 计为 Claim 修饰。组文本按时间序 `\n` 连接、**代表=最后一条**。
  - **处理不推迟**：首条立即处理；**补充到达即更新**（同一分组重算），"追加更新"与"新消息更新"同源一致。**测试==实际**、**实时==重放**（分组为日志的确定性函数，共用 `src/parser/coalesce.rs`）。
  - **匿名代排 `X(代)`**：该行填 `发送者(代)`（匿名、代群外）；**校验按代排者（发送者）**——发送者可排 ⇒ 可排；**锁定仍生效**；`代排` 不改变归属显示的被代人名（匿名无名字）。
  - **展示**：消息流**逐条不合并**；成员行标 `Merged`。
  - **配置**：`merge.enabled`（默认关，实验）+ `merge.same_sender`。
  - 实现路径：统一入口 `Pipeline::ingest`（NC 与 sim 共用）+ 以日志为准的 `recompute`；重放 `compute` 同函数分组。
- **回复**：用户确认"同意图/无窗口/相邻/不推迟/测试同路径/代排视为 Claim 修饰/闲聊保持 Ignored/代排校验按发送者/展示不合并/代表取最后一条"，并要求 README 加开发中告警。
- **影响**：`src/parser/coalesce.rs`(新)、`src/llm/pipeline/mod.rs`(+`state.rs`)、`src/replay/session/mod.rs`、`src/services/replay.rs`、`src/settings/mod.rs`、`src/api/sim_routes.rs`、`web/{display.js,replay.js,display.css,theme.css}`、`README.md`、`tests/e2e/sim.mjs`。详见 [SPEC-MESSAGE-MERGE.md](./SPEC-MESSAGE-MERGE.md)。

### B-6 唯一事件处理链（统一处理 + 阶段锁 + computed 缓存）`已决策`（2026-10-13）
- **结论**：
  - **只有唯一事件处理**：`传入消息 → 落盘储存 → 即时重算(live) / 分步重算检查(复盘)`；禁止实时/重放双路径。
  - 数据流：NC→原始消息落盘→LLM 处理→override 落盘→compute(日志) 产生动作记录→**增量 compute**（除非 override 刷新，否则不全量）→读取(Live/复盘)。**前端只读取不计算**。
  - **`State.locked` 移除**，改用**阶段锁**（"快进到下一阶段"；阶段 ∈ {Settling, Locked} 即锁）；**未到结算阶段也可模拟分包**（试算/分包不受阶段锁门禁）。
  - **动作记录/看板持久化**到 `data/computed/<round>.json`（读取层缓存，含完整性哈希）；activate：`continue`=加载 / `fresh`=清空 / `replay`=全量。
  - `merge.enabled` 保留、**默认开**；复盘分步**按消息组**（组内追加不产生新步）。
  - 增量粒度：**解析级增量 + 看板全量重建**（引擎级增量留作后续优化）。
  - **消息编辑受阶段锁控制**；**不引入本机会话 token**。
  - Git：**先清洗历史（filter-repo 去真实群号/昵称/IP）→ 再重签全部分支提交 → 协调 force-push**。
- **回复**：用户确认方案 B 完整版、清后重签、接受 merge 默认开、编辑受锁、不加 token；activate 缓存策略按默认（continue/fresh/replay）。
- **影响**：见 [SPEC-UNIFIED-PIPELINE.md](./SPEC-UNIFIED-PIPELINE.md) §6。

## H. 2026-10-16 消息人工修订口径（已确认，授权分批实施）

> 来源：用户对消息流程的明确回复。实施步骤与代码草案见 [专项计划](./PLAN-message-reprocess-2026-10-15.md)，提议归纳见 [用户提议](./USER-PROPOSALS-2026-10-16.md)。未完整实现、未部署；旧冲突提案集中列在本文末节。

| # | 用户确认的方向 |
| --- | --- |
| H-1 原意与位置 | 管理员修订是纠正当时意思，由管理员解释；原消息位置/时间不变。原有后续操作继续保留执行，尤其撤排、改单，不以旧快照抹去后续历史。 |
| H-2 手工合并 | 连续或不连续的补充性解释，可等效为“修改第一条完整动作，拒绝后续补充条”；不是多笔独立订单共同交给 LLM。主条与补充条一起保存、重算，原消息各留原位。 |
| H-3 原自动与人工动作 | 原始自动处理结果完整保留。管理员从当前动作草稿直接改错处，可附解释；程序生成完整替换 override，不追加原动作。保存/执行不再让 LLM 重新理解；可选草稿代填见 H-7。 |
| H-4 优先名单 | 修改名单只更新权限并逻辑重算，复用已理解的自动/人工动作，不重跑 LLM。原自动判定与当前权限结果分开保存/展示。 |
| H-5 人工时序 | 自动理解先于人工可观测的动作。人工忽略、拒绝、恢复均通过动作/有效选择修订，不另造“人工先忽略、再首次 LLM”的流程，也不要求恢复时重新问 LLM。 |
| H-6 保存与撤回 | 普通修订不需要二次确认，一次保存重算即可；拟提供单步撤回，用户提出可备份上一完整状态。技术建议为完整逻辑检查点 + 撤销最近人工事务后重放当前日志，不直接覆盖掉之后新消息；该恢复机制仍需验证。 |
| H-7 低负担编辑与可选代填 | 用户同日接受“可点改动作句 + 可选一句话 LLM 代填”。默认复制当前动作，只改错处，其余字段由程序带入；复杂解释主动代填到同一草稿，填错可手改，不接触/复制 JSON。代填不自动保存，保存/重算仍 0 LLM、一次提交并可撤回；不授权真实模型测试或部署。 |
| H-8 排撤分离与原申购撤销 | 排、撤是不同语义，不自动合并。甲排商品 A 获位次 B，之后撤 A，若之间没有再次加排 A，则撤掉这笔 B 位的认购；紧跟/不紧跟、有其他发言都不改变目标。保留原时间和后续操作；本例不授权将多次加排一概解释为撤全部历史单。 |

实施边界：已授权本专项分批开发；不改变确定性校验/权限和真实群安全红线，不因动作 override 赋予原发送者管理员身份。完整自动动作持久化、撤销目标稳定引用、检查点原子恢复属于工程前置门禁。不授权生产迁移、部署/重启、通用全系统回滚或无限撤销。

## 已舍弃的功能或思路（2026-10-16起；后续补充）

以下旧建议已被 H-1…H-8 取代，不是继续排队的待办：

旧diff实现中的“进程全局round_id→最后一次ReplayResult”、GET隐含继承上次预览及写入口remember钩子已弃用，由M的当前上下文诊断/本次显式预览分离取代。实际隔离复现新消息后陈旧结果及不同实例同round_id串用，不能仅补round_id键或把旧预览冒充当前数据。

代排旧实现中的“HashMap首个精确/包含名即归成员”“全部未命中以显示名合成身份并用该标签判资格”不再使用；由L的唯一成员/真实发言人两类规则取代。旧冻结记录不自动重解析，缺真实发言人的历史代排先核对，不靠猜测补身份。

- 人工纠错强制重新调用 LLM，以及“解析预览→二次确认”：改为动作句编辑、可选代填、一次保存。
- 多笔独立订单的人工联合 LLM 理解：改为补充说明的主条替换与补充条拒绝；排与撤绝不自动合并。
- 名单/别名保存后自动批量重跑 LLM 覆盖 ParseOverride：名单只权限重算；人工结果不可被自动刷新覆盖。
- 正常人工修订直接改成员原文、或要求填写动作 JSON：保留原文，独立解释，由界面生成完整动作。
- 显示 seq 作为管理写入键：只允许稳定记录身份与版本守卫，seq 仅保留排序用途。
- 将旧完整文件/看板覆盖回来撤回：保留完整逻辑检查点，逆转最近人工事务后重放当前流，不丢新消息。
