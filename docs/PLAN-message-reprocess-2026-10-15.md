## 1. 已确认的业务模型

自动处理先产出可供人工查看的结果，管理员从当前动作复制的草稿开始，只改错处；复杂说明可选 LLM 代填同一草稿，仍可直接手改。保存时由程序构造**完整替换动作**，附管理员解释。自动原结果永久保留，实际处理选取人工 override；没有 override 才使用自动动作。

    原消息 → 自动理解结果与原动作（保留）
                             ↓ 作为编辑初值
                点改 / 可选代填 → 同一动作草稿
                             ↓ 管理员一次保存
                  完整动作 override + 解释
                             ↓ 一次保存，不再问 LLM
           在原消息位置选择有效动作 → 权限判定 → 按全流重算
                             ↓
                 原行、排位、汇总更新 + 单步撤回

1. 修订解释的是**当时的意思**，由管理员判断。系统不另造“后来改变主意”的业务分支，也不让 LLM 对管理员解释反复裁决。
2. 原消息身份、时间、顺序保持；修订时间仅进审计。修正内容可以影响排位，但不变成排到末尾的新申购。
3. 原消息之后的其他操作照常保留，尤其撤排、改单、其他成员发言；替换早期动作后必须继续执行它们，不能用旧排位快照覆盖掉后续历史。
4. 手工合并是补充性解释，支持连续或不连续发言：**修正第一条的完整动作，拒绝/停用后续被吸收的补充条**，不是新建一条合并消息。
5. 修改优先名单只是重新判断权限并逻辑重算；动作已理解，不重新调用 LLM。
6. 每次修订只需一次“保存并重算”，不另弹确认；提供最近一笔人工事务的单步撤回。撤回的技术边界见 §8。
7. LLM 可帮助填写，但不是必经处理链、批准者或执行者。代填不自动保存，填错直接手改；不需要复制/填写 JSON，不另设一套 AI 编辑器。
8. **排、撤不同语义，绝不自动合并**。甲先排商品 A 得到位次 B，之后撤 A，只要之间没有再次加排 A，就撤掉这笔原申购；是否紧跟、隔了多久、有无其他发言均不改变目标。撤销记录仍在自己的原时刻执行，不把撤销拼进早期申购文字。

## 3. 三层结果与有效动作选择

### 3.1 必须保留的三层

- **原始事实**：原文、消息号、真实发送者/代理来源、群、时间、seq、record_id。普通修订不改这些值。
- **原自动结果**：当次自动理解的完整动作/候选、理解来源、初始分类和当时处理结果/原因。追加保留，不被人工替换或权限重算覆盖。
- **人工修订**：完整替换动作集、解释、关联补充条、人工忽略/拒绝决定、操作者和修订时间。多次修订保留历史，只选择当前有效版本。

“初次自动判定”与“当前执行结果”不同：原来已理解但因非优先被拒绝，修改优先名单后可变为当前 Applied，而原始自动 Rejected 记录仍保留供复盘。

### 3.2 选择规则

    存在有效人工 override：使用该版本完整动作/人工拒绝决定
    否则：使用已持久化的自动动作
    然后统一做当前业务校验、权限判定与确定性重放

- override 是**替换完整动作集**，不是在自动动作后追加一套，不是文本差异补丁。
- 人工明确空动作集是有效选择，绝不能因 [] 为空就回退自动动作。人工忽略/拒绝都不产生排位动作，但标识与解释可区分。
- “恢复自动”明确选择原自动动作，再按当前权限重算，不调用 LLM。“撤回上一步”恢复前一人工选择，二者不能同名。
- 自动结果仍不完整/待确认时，管理员直接补齐完整动作；自动处理中尚无可编辑基线时显示处理中，不设计“先人工忽略、再首次 LLM”的倒置流程。自动处理失败后也可记录错误基线并人工补正，无须等待模型成功。
- 普通重算、政策更新、刷新、复盘和撤回均不调用 LLM。后续自动产物不得悄悄覆盖现有人工选择。

### 3.3 动作编辑范围

采用可点改的动作句，例如“排〔立牌·甲〕〔2〕份”；常用字段直接改，相关策略按需展开，支持多行及明确行序。程序从当前有效动作带入其余字段，保存完整动作集，不要求管理员重新填满所有字段。数量和目录 ID 等由确定性逻辑检查。

不让管理员手填任意领域事件 JSON，也不借此加入群发送、阶段命令、身份提权或资金修改。业务动作仍按原消息真实身份与权限计算；需改权限时走相应设置，不能伪造原消息 is_admin。

“管理员解释”默认用于人工理解与复盘；只有主动点击代填时才可作为该次草稿请求的输入，保存/重算不再拿解释去问 LLM。解释独立于成员原文，只改解释不改变已选择的动作。

## 4. 交互：选取 → 编辑动作 → 一次保存 → 原位重算

1. 点击任何可见状态的消息，打开同一详情侧栏。查看原文、原自动动作/状态、当前有效动作、当前权限原因与管理员解释。
2. 默认从当前有效动作开始编辑，原自动结果放只读对照；选择“恢复自动”时明确显示将恢复的内容。
3. 直接点改动作，或写解释后主动点“AI 代填草稿”；两条路径写入同一草稿。补充性合并选取主记录和补充条，连续/不连续都支持。
4. 点击**保存并重算**，服务端校验→备份检查点→提交覆盖→全流重算→原位发布。无“再解析”、无预览后第二个确认按钮，不逐字自动保存。
5. 保存成功显示已生效摘要和差异，提供“撤回上一步”；失败就地显示原因、保留草稿。结构错误阻止保存；动作合法但权限拒绝可保留修订，并明确当前仍拒绝。
6. 更新不跳底、不重载、不丢选中文字、筛选、滚动和焦点。修订后不再符合筛选时，保留打开详情并提示可返回全部。

校验失败、409 冲突、锁定提示不是额外确认步骤，而是无法安全应用时的反馈。单纯保存不新增全局确认弹窗；已有独立危险操作的确认策略不被本条取消。

### 4.1 低负担编辑区（已接受）

- 默认就能点改当前动作里的排/撤/改、商品与子项、数量；商品支持搜索候选，不显示内部 ID。不让管理员面对空白大表单。
- 单领/拼团、包尾/包盒及具体撤销目标等随动作类型按需出现；不同时展开所有动作的所有字段，不隐藏当前已生效的重要策略。
- 原自动结果、历史修订折叠只读；当前执行动作始终有摘要。保留“添加动作”“更多处理”以覆盖复杂情况，但不要求普通修改先选操作模式。
- 管理员解释与“AI 代填草稿”在同一可展开区域；手工输入与代填不切换页面，不另外增加接受建议/确认应用层。
- 简单纠错是“点改一个字段→保存”，复杂纠错是“一句解释→代填→可手改→保存”；JSON 的生成、目标 ID 与完整替换都由程序承担。

### 4.2 可选 LLM 只做草稿助手

- 只有明确点击才调用当前已配置的模型；输入、打开消息、展开解释、保存、恢复、撤回、优先名单重算均不触发调用，不做每字自动请求或隐式批量重解析。
- 请求只包含选定原文/补充、管理员说明、当前草稿和必要目录；说明发送范围与服务，不发送完整群名单、原始 NC JSON 或整段聊天。注释不能变成系统指令或管理权限。
- 返回结构经目录/数量/动作 schema 检查后填入**当前草稿**，标出被改字段；仍可直接点改。未明确的字段留候选/就地问题，不猜一个值来强行通过，也不把 JSON 错误转交管理员修理。
- 代填不写有效 override、不重算、不拒绝任何消息、不改变主锚点/关联范围或优先权限；选中补充条的人工拒绝仍随最后一次保存整笔提交。
- 请求绑定实例/轮次/记录/草稿版本；等待时手工已改内容、再次发起请求或切换记录，旧返回不得覆盖新草稿。可取消旧请求，不自动循环重试。
- 模型关闭、超时、失败或返回不可用：原草稿与已发布动作保留，提示可直接手改。模型可用性不阻塞手工保存，失败不偷偷套规则或另一模型自动提交。
- 保存只执行界面显示、管理员最终选择的动作；此阶段模型调用数为 0。审计可标来源“人工直接编辑/AI 代填后人工保存”，但最终决定仍是人工保存。
- 前轮占位交互草图已验证点改、代填后手改、一次保存、原自动结果保留、忽略和撤回；代填为本地模拟，**不等于真实 LLM/业务链已接线**。

## 5. 手工合并等效为一次多记录修订

### 5.1 操作语义

- 第一条是被纠正的主消息，管理员给出它**完整的最终动作**和解释。
- 后续选中的补充条记为人工拒绝/停用，原行留下“补充已纳入主消息”及双向定位；原文和原自动动作完整保留。
- 主条与补充条**一次原子保存、一次重算、作为一笔可撤回事务**。不能先改第一条已生效，再因第二条停用失败而重复计数。
- 原行都不移动、不删除，不新建合并消息。中间不相关发言及之后撤排/改单继续在原位置执行。
- 不是多笔独立订单的联合 LLM 理解。管理员裁定补充含义；可主动请模型代填动作草稿，但不能让模型自动决定主条、关联范围、权限或最终执行。

### 5.2 与已有自动合并衔接

- 人工 override/人工拒绝先于自动分组生效；人工固定单元及被吸收补充条不能又被自动合并消费。
- 自动结果若来自组级聚合，详情展示整组成员与原自动动作；不能假装每个成员已各有一份独立完整动作。
- 编辑落在原自动组内部时，事务明确覆盖的实际自动执行单元，并列出受影响成员。剩余成员如何执行必须能由完整替换动作确定；不沿用含已停用文本的旧聚合动作，不静默丢掉未选成员，不强制重跑 LLM。管理员仍可主动代填草稿后自行修正。
- 禁止循环、同一补充同时归两主消息、跨实例/轮次/群的执行关联；结构冲突就地提示，不保存半套状态。
- 后续新入站不能把人工单元重新并回旧 merge_open；分组缓存随覆盖发布失效。未受人工修订的自动组仍遵循既有组末代表规则。
- 将自动组纠正为“第一条替换 + 补充条拒绝”属于显式人工覆盖，**按主条原时间执行**；它不修改原自动分组记录，也不改其他自动组的默认规则。

## 6. 保留后续操作：重放全流，而非恢复旧排位

示意：主消息原位置的 Claim 被改正 → 中间消息保持 → 补充条停用 → 后来的 Cancel 仍执行。最终不能因修正早期 Claim 而让后来的撤排消失。

例如先排 2、后来撤全部，将早期动作改为排 3 后，最终仍应为 0；若后来动作仅撤 1，则按其原语义重放后为 2，而不是停留在某份旧快照的数量。

- 从有效动作源重建整轮事件序列，用原 (timestamp_ms, seq) 及消息内明确动作次序处理。原位修订不追加当前时刻的 Modify。
- 原消息本来是 Modify 时，仍保留“撤旧+重排”的业务语义，使用该条原时间，而不是管理员编辑时刻。
- record_id 之外要有稳定动作/claim 身份。当前重放按 seq 派生标识，迁移时保留映射，不能因编辑排序或新 UUID 打断后续精确撤销引用。
- 现有按 claim_id 撤、按商品撤、撤最近一单是不同语义：都保留原目标/条件与执行顺序，不自动改写后续动作来配合前条修订。精确引用继续指向对应稳定动作；商品条件找不到时说明未命中，不能悄悄改撤另一商品。
- 修订移除被引用动作时，保留后续撤销记录并显示目标失效/未命中原因。需修正后条时由管理员编辑后条，不删除原记录或暗中再让 LLM 改写。
- 单条替换可改变最终占位；系统保证原时序和后续操作被执行，不承诺所有格子位置不变。

## 7. 权限更新只做逻辑重算

- 优先名单修改后，复用每条已保存的自动动作或有效人工动作，重新判定资格/优先级并全轮重算；**LLM 调用次数必须为 0**。
- 初次因优先权限 Rejected 的完整动作仍需可取回；若过去只存 Rejected 字符串而没存动作，不能伪称已支持。应标明缺失，由人工补正或另定历史补齐方案，不隐式批量问模型。
- 从拒绝原因可直达“轮次与商品·优先成员/时段/阶段”，保存后返回原消息并显示新结果；不自动加入成员，不激活其他轮次，不更改消息时间。
- 政策影响整轮，不假装只放行跳转来源这一条；人工拒绝/忽略仍有效，不能被新名单自动复活。影响摘要在保存后展示，不要求第二次确认。
- 群/成员白名单、阶段与锁仍走共享确定性政策；人工动作不是绕过安全边界的原始事件注入。当前锁中不发布修订，仍需明确解锁。
- 历史手动阶段复现与 UP-01 一起验证，不能把“目前解锁”当作“锁期原消息当时允许”的证据；本计划不顺带改阶段业务政策。

## 8. 单步撤回与完整检查点（实现建议，待验证）

用户同意的方向是无需二次确认，并可提供单步撤回；以下为避免丢后续数据的实现约束，不声称已有功能。

### 8.1 撤回什么

- 首版支持**最近一次成功的消息人工事务**，包括动作替换、解释、人工忽略/拒绝、恢复自动以及“主条修改+补充条拒绝”的整笔合并。
- 保存前持久化上一完整、可重建的轮次逻辑状态检查点：原消息/自动结果引用及游标、当前人工选择/关联、政策版本、排位/汇总和相关结算版本。原始日志不可变部分可用校验引用，不必每次复制所有 NC 原始数据。
- 同时保留本事务触及字段的前值/后值、稳定目标版本、事务号和撤回令牌。完整检查点用于恢复/核对；撤回实际采用“撤销这笔人工改动 + 在当前日志上重放”，不物理删除后来的日志。
- 只留一个可用的单步撤回槽，不同时引入任意历史跳转或无限 redo。后续成功人工事务更新此槽，失败保存不覆盖它。政策设置的通用撤回不在首版消息撤回范围内，不因此许诺一键倒回全部系统配置。

### 8.2 为什么不能直接覆盖旧快照

保存修订后又收到新消息或撤排，再点撤回：恢复该人工事务之前的有效动作选择，**然后保留新消息、新撤排继续重算**。不能把整个仓库、轮次日志或当前排位硬盖成备份时的样子。

- 没有其他变化时，撤回后的业务状态与操作前相同；新审计/版本号不倒退。
- 有后续新入站时，撤回保留它们；不丢消息、不恢复已被后续撤排取消的认购、不重跑 LLM。
- 若另一人工事务改了同一目标、配置/阶段导致基线不可用，或当前已锁/切轮，按版本检查拒绝过期撤回并说明原因；不盲目回退别人的修改或自动解锁。
- 撤回也是新审计事务，原自动结果和修订历史不删除；成功后消费撤回槽，不把“撤回本身”变成反复切换的 redo。
- 检查点在私有运行目录持久化，成功应答前可恢复；重启后不能只剩无效“撤回”按钮。
- 不把旧结算草稿/订单号硬盖回来；恢复动作后重新标记或校验结算依赖，保留当前人工订单数据。

## 9. 数据与提交契约（拟议，非现有 DTO）

| 层 | 必需内容 | 目的 |
| --- | --- | --- |
| 原记录 | round_id、record_id、原时间/seq/身份/原文 | 稳定锚点，永不以显示 seq 作写目标 |
| 自动结果版本 | 自动单元/成员、解析来源与动作、原判定/原因、目录/输入版本 | 修订后仍可复盘自动为何如此处理；权限拒绝不丢已理解动作 |
| 人工覆盖版本 | 完整动作集/空集及处置、解释、补充条关系、基线版本、操作者、时间 | 当前实际使用版本，可撤回；不与自动结果混存互相覆写 |
| 有效动作选择 | auto 或具体 override_id、来源 record/action_id | 仅一套动作执行，恢复自动不重新解析 |
| 提交/撤回信息 | transaction_id、幂等键、记录版本、前后值、检查点/撤回令牌 | 多记录原子保存、幂等、冲突与恢复 |
| 已发布投影 | view_revision、消息当前状态/原因、排位/汇总、依赖版本 | 旧行更新、跨页一致，事件数量不变也能通知 |

- 写入带预期实例/round_id、record_id/组及覆盖版本；旧可选 revision 的无条件写不能继续作为安全入口。新 DTO/路径实施前落定 TASKS/INTERFACES，不修改冻结 bus 绕路。
- 动作内部顺序明确；稳定动作 ID 与显示行号分开。新增/删除行可改变动作集，但不能把后续引用偷偷指向别的行。
- 旧 ParseOverride 不能一概视为原自动结果：区分原 LLM 澄清和人工确认来源。无法可靠区分/关联时标“历史来源不明”，保留原始事件并要求核对，不猜测迁移。
- 原消息被旧编辑器改写的，无法证明的更早原文不得伪造恢复；迁移前私有备份，标明恢复边界。
- 当前本机无可靠登录身份时，操作者标本机管理员/未认证身份，不能把浏览器自报名当鉴权；不开放公网管理。

### 9.1 一次提交

短事务内读取最新轮次与记录→校验动作/关联和版本→持久化可恢复检查点→以完整替换选择重放当前全流→提交修订/选择/结果→同代发布。新消息仍可进入入站队列；重算与入站提交按轮串行，基线有新消息就纳入，不用过期全量文件盖掉它。

多文件不天然有事务：采用统一提交日志/标记与可重建投影等方式实现逻辑原子性，须通过写入失败和崩溃恢复测试。不能先返回成功，再发现解释、补充条或排位只保存一半。

结构不合法时保持上一已发布结果、保留草稿；语义已明确但权限仍拒绝时，可保存 override 并发布拒绝结果。重算失败不能假报成功或把自动结果清空。

## 10. 实时显示与复盘

- 消息流主体保留成员原文，附“人工修订/人工拒绝/补充已纳入”等标识及当前动作摘要；管理员解释独立显示，不伪装成成员原话。
- 详情分清“原自动结果”“当前实际执行动作”“本次编辑”；复盘同时可查原自动结果和解释。当前轮复盘按有效动作重建，末步与实时一致；不声称复原每个时刻的旧配置。
- 提交记录可追溯到原消息；审计在修改时刻追加，业务动作仍在原时序执行，不另加队尾申购步骤。
- 独立 view_revision/epoch 通知老记录 upsert；原 seq 不为刷新而改变，不与排位版本混用。断线/过期游标提供完整对账，分页外旧行也可定位。
- 同代返回消息、排位、汇总；按 record_id 保留 DOM/焦点/划词/滚动。旧行更新不算新增，不强制滚底。
- 政策更新即使消息数、事件数不变，也触发当前权限结果/复盘刷新。原自动动作与人工动作不因展示重算改变。
- 原文、管理员解释、自动基线、修订、检查点均属私有运行数据；未来共享只发布脱敏投影，不导出 NC 原始日志或管理审计。
- 电脑端 1920×1080、100%、DPR=1 验收；密集信息保留，详情操作有名称、滚动可达、键盘可用，明暗均可辨。

enum ActionSelection {
    Automatic { note: String },
    Replace { actions: Vec<EditableAction>, note: String },
    Ignore { note: String },
    Reject { note: String },

fn effective_actions(auto: &AutomaticResult, choice: &ActionSelection) -> Vec<EditableAction> {

### 15.3 稳定动作与撤销：位置不是新申购

第三批实际结构（省略商品项策略等字段；完整字段见源码），不将多项原申购拆成无法整体引用的独立 claim：

```rust
// 单条动作行的 identity 独立于数量、商品文字与管理员修订时间。
struct EditableAction {
    action_id: String,
    operation: Operation, // Claim / Cancel / Modify
    items: Vec<EditableItem>, // 排/改：原申购的全部商品项
    target_claim_id: Option<String>, // 撤：具体原申购（不与下面条件混用）
    target_item_id: Option<String>, // 撤：商品条件；都为空=最近一笔
    quantity: Option<u32>, // 商品条件撤全部用 None；具体 claim 不带数量
}
struct EditableItem {
    line_id: String,
    item_id: String,
    subitem_id: Option<String>,
    quantity: u32, // 1–99
    // claim_type / slot_policy / is_proxy_card / notes 保真，不接收任意 admin event
}
// primary 继承原认购 ID（含旧 seq 派生标识）；新增动作按 record_id+action_id 派生。
// 按原 (timestamp_ms, seq, action_order) 顺序执行。
// 有明确引用则按引用；明确商品/数量则按原条件；无匹配显示未命中。
```

同人 Claim(A) 与 Cancel(A) 的分组键必须不同；优先权只影响分配，不把其他人的 A 当撤销目标。未再次加排 A 的确认用例必须撤掉原 B 位上的认购。重算早期 Claim 后继续消费后续 Cancel，而非直接返回编辑时备份的 board。界面保留已失效的精确目标引用，不偷偷改撤另笔；引擎逐条未命中原因的完整展示仍待 MP-6。

用户最新授权：先签名提交/推送前三批已验收结果，随后继续剩余消息专项及已计划的信息架构整并，并完成测试。远程 origin/当前分支在提交前重新读取且无分叉；不因推送获得部署、真实数据迁移或真实群/模型调用授权。

本批补 MP-1 选择真源和 MP-2 手工编辑；多记录合并、单步撤回、显式模型代填、独立投影版本仍另批，不用假按钮冒充可用能力。所有状态的本地消息可打开同一编辑器，从当前动作带入，原自动结果只读对照。

```rust
// HTTP 只收业务动作，不收任意领域事件/身份/时间/管理员命令。
struct SaveActions {
    transaction_id: String, round_id: String,
    config_revision: u64, record_revision: u64,
    selection: ActionSelection, // automatic | replace | ignore | reject，含独立解释
}
// 一个申购动作可含多项，保留原 claim 整体引用；项和动作各有稳定 ID。
// 撤销明确区分原 claim / 商品数量 / 最近一单，不能猜测扩成撤全部。
// 普通保存先在内存准备并全流重算，校验成功后持久一条选择事件，再发布。
```

- `POST /api/messages/:record_id/actions` 带必需轮次/配置/记录版本与幂等键；同键同内容不重复保存，同键异内容冲突。选择事件单条持久，失败不发布成功；不先写解释再写动作。旧 `/override` 与新选择按事件顺序择一，不执行两套动作。
- 新选择扩展现有 `ParseOverride` 的私有版本化载荷，明确区分旧解析结果；不得将新选择误认成原 LLM 结果。重放读取已保存规范动作，只重验政策；恢复自动只用已存匹配产物，缺失则阻止恢复并保留当前选择。
- 动作/项使用稳定 ID，初始申购继续使用原 claim ID；编辑数量或重排行不能换成新单。先限制同条显式目标不得指向自身/未来/他人；删除目标后的后条不偷改指向。保存保留原时间/seq/身份/原文。
- 本批单条提交不改原消息日志，只追加管理选择并发布派生结果；当前结果读取由有效选择重建。跨文件全局事务/所有旧维护写入口仍未完成，不能宣称生产升级安全。
- 界面不输入 JSON；常用字段直接改，撤销目标/策略渐进展开；一次保存，无第二确认。错误保留草稿，等待加载或保存时防止重复提交和关闭后错误更新；焦点、滚动、划词与键盘均回归。
- 新增隔离回归覆盖四种选择、空覆盖、动作/原 claim 身份、多动作顺序、后续撤排、目标越权/过期、缺失自动基线、幂等、存储失败和重启重放；1920×1080/100% 真实页面测试并留截图。实际完成范围、门禁在 §16 续记。

## 18. 已舍弃的功能或思路

以下已从当前实施步骤移出，**禁止照旧实现**：

| 旧提案/旧路径 | 舍弃原因与替代 |
| --- | --- |
| 人工改原文→强制再次 LLM→解析预览→二次确认 | 管理直接修动作；可选代填同一草稿，一次保存，执行 0 LLM |
| 将多笔独立订单交给 LLM 联合理解 | 手工合并只指补充说明：第一条完整替换、补充条拒绝；排与撤不合并 |
| 别名/名单保存自动批量重跑 LLM 覆盖既有 ParseOverride | 名单只重验权限，已有人工选择不被自动产物覆盖；显式草稿请求不批量执行 |
| 原始消息文本编辑作为日常纠错入口 | 原文保留；修订动作和独立管理员解释，旧数据管理能力迁出日常工作流 |
| 用显示 seq（或 record_id 缺失就回退 seq）写消息 | seq 存在内存/落盘分歧；只用稳定 record_id 与版本守卫 |
| 完整状态备份后直接覆盖旧文件/旧 board 作为撤回 | 会丢后续新消息；保留完整逻辑检查点但用人工事务逆转后重放当前日志 |
| 另开 JSON 编辑器/要求管理员填写完整动作对象 | 完整对象由程序生成；动作句点改，可选代填 |
| “排 A、撤 A 的间隔”是待确认合并条件 | 已由用户明确为不同语义，间隔不改变撤销关系；见 H-8 |
